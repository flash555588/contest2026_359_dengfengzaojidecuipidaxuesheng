# 网络直播（新版 v3 系统）

原生 LVGL 应用，直接请求 B站、虎牙、网易CC 房间 API、取得 H.264/FLV CDN 地址并由 OpenH264 2.6.0 软件解码。
入口为“全部应用”第一页的“网络直播”，用下拉菜单选择平台，输入数字房间号后播放。网络沿用新版 C6 Wi-Fi、DHCP 和时间同步；没有另建网络服务。
HTTPS 直接调用桌面的 `glass_https_tls_ops()`，使用原有 mbedTLS、证书校验、TLS 1.3 ticket
处理、取消和空闲超时机制。持续收到数据会续期，停止播放会取消请求。

直播使用单线程 H.264 解码，AAC-LC 音频复用本地播放器的 Helix 和板载 PCM 输出；暂不支持弹幕。
视频解码、AAC 播放与 FLV 取流独立运行。压缩视频最多排队 6 帧 / 2 MiB，音频最多 256 个包 / 256 KiB；
音频另有时间上限：缓存超过 1000 ms 时丢弃旧压缩包，保留最近约 250 ms，
继续使用已打开的 PCM 设备。这样可消除未触及包数上限的长期积压；突发期间可能跳过声音。
界面“音画”是视频相对播放时钟的差，“缓存”是压缩音频队列时长，
“视频”是当前解码画面落后最新接收视频时间戳的时长；均不代表主播到屏幕的端到端延迟。
过时非参考帧可直接跳过，视频队列积压则保留下一个依赖帧以释放解码器延迟输出，再等待新的 IDR，携带最新 SPS/PPS 恢复。
音频独立播放并提供显示时钟；停止或切换会先取消、唤醒并加入音视频线程，再释放资源。

虎牙根据接口公布的兼容 AVC 档位选择最低正码率，沿用 Pure Live 网页 AntiCode 模板算法，
MD5 和 Base64 直接复用现有 TLS/PSA 库。保留服务端到期时间，尚未移植 WUP 长会话续期。
网易CC 根据接口的最低可用 Ali CDN 档位选择对应 streamname/token，以 `/live/<streamname>.flv`
直接取流；房间重定向入口会忽略档位并返回原画，不能用于低清播放。
本次实测虎牙 660000、11342412 的 500 kbps 及 CC 163163、5200 的 600 kbps 均为 800×450。
码率档位不是分辨率保证，界面以实际解码尺寸为准；超过上限会停止，不盲目分配大解码缓冲。
画面显示为 640×360 RGB565，码流限制为 1280×720、
渐进 8 bit I420 和有界参考帧/FLV 缓冲。B站优先向 v1 `playUrl/playUrl` 请求 qn=80 的低清 FLV；
接口没有可用低清线路时，回到原来的 v2 `getRoomPlayInfo`、qn=80 路线。
服务端实际清晰度和正在播放的房间号在界面显示。
播放中输入新房间并点击“播放”会取消旧任务、回收后启动新房间；停止或退出取消待切换请求。
2026-10-13 实测房间 6：v2 匿名请求 qn=80/150 仍返回 qn=250、1280×720，
v1 qn=150 实际返回 H.264 High、854×480。清晰度列表不能代替真实码流尺寸检查。
支持最多三条 CDN 线路和三次重定向，拒绝 HTTPS 降级。退出、返回或切换应用取消旧会话。
可选登录 Cookie 从 `/data/bili_cookie.txt` 读取，不打印 Cookie 或签名播放地址。

## 单板运行与性能实测

播放过程由 P4/C6 独立完成，电脑只用于编译、烧录和准备离线测试素材。
2026-10-13，现有 OpenH264/Helix 播放器在板上完成两份 8 秒、10 fps、
Baseline H.264 + AAC 的本地素材测试，均正常结束。前 60 个样本中，
640×360 显示 45 帧、丢 15 帧，累计读取/解码/渲染/等待约 6.31 秒；
848×480 显示 31 帧、丢 29 帧，累计约 8.03 秒。
这些计数是渲染提交次数，不等同于 LCD 刷新计数，也不能代表长时间直播表现。
现阶段尚未实现稳定 10 fps；480p 测试仅解码就平均耗时约 103 ms/样本。

同日进一步优化：C++ 解码器采用 `-O2`，并将一组运动补偿、反变换和
CAVLC/CABAC 函数放入内部指令 RAM；不改变解码运算、参考帧或码流质量。
内部代码段增加约 12 KiB，会相应减少内部堆空间。相同 848×480 素材，
优化前后各两次测试，前 60 个样本的平均解码耗时从 6135 ms 降到 5750 ms，
约减少 6.3%；640×360 从原先一次测得的 4290 ms 降到两次平均 4115 ms。
360p 使用内部 RAM 的平均耗时与仅使用 `-O2` 相同。解码计时排除了帧回调，
仍包含调度抢占时间；短样本结果不能代表所有码流，也不表示已达到 10 fps。

同日继续实测：仅在播放期间将视频工作线程固定到 CPU1、音频与桌面固定到 CPU0，
结束后恢复桌面的双核调度范围。本轮重新烧录原内部 RAM 版本测得的 480p 前 60
样本解码时间为 5840/5940 ms，新版本为 5350/5390 ms，平均减少约 8.8%；
仍有 28/29 帧未提交显示，不能宣称 480p 稳定 10 fps。360p 本地 AAC 音视频
两轮前 60 样本解码时间为 3630/3600 ms，均提交 60 帧、丢帧 0，
读取、解码、渲染和等待的合计为 6150/6170 ms；这不是 LCD 刷新计数。

提供独立诊断 `desktop decode-bench /sdcard/<name>.mp4 0`，跳过音频和渲染，
对所有可见 I420 像素计算滚动哈希并从解码计时中扣除回调耗时。

2026-10-13 增加直播与本地播放器的屏幕对比信息：每两秒采样解码 FPS、画面 FPS、
每帧解码/颜色转换耗时及待显示画面的覆盖次数。画面 FPS 统计 LVGL 接收图像的次数，
不能直接当作物理 LCD 刷新率；全屏时信息移至底部。直播纯解码耗时排除帧回调与音画等待。
`desktop media-fps 5|10|15|20` 调节落后画面的提交上限，默认 10；它不是性能保证。
AAC 工作线程固定 CPU0、优先级 120。默认保留 256 KiB L2 / 64 字节缓存行；
512 KiB / 128 字节实验版本烧录后两次复位没有 NSH 输出，已撤回，未获得性能数据。

同日同固件测试原生 High Profile、25 fps、4 秒 H.264/AAC 本地素材（400 kbps、
4 个参考帧、2 个 B 帧）：640×360 两次纯解码 100 帧用时 6570/6640 ms，
848×480 为 10640/10380 ms，平均纯解码速率约 15.1/9.5 fps。
两种尺寸各自重复的输出哈希一致，且与同一修改版 OpenH264 的主机输出一致。
这些素材不是直播源；运行阶段没有主机转码或中继。
360p 带 AAC 与 UI 的本地播放中段约 8～9 次画面提交/秒：提交上限 5/10/20 时，
100 个解码画面分别提交 42/96/100 帧，LVGL 接收 39/95/99 帧。
高上限测试仍未证明稳定 10 fps；解码与转换占用了主要处理时间。
原始证据保存在本地 `output/media-v3-fps-final/`。
同固件、同原生 360p 文件进一步比较颜色转换：前 60 个样本软件/PPA 转换为
2100/1480 ms，两者均提交 58 帧；PPA 约减少 29.5% 转换时间，继续保留 PPA。
最终固件的约一分钟 B站 854×480 检查段，最后快照解码 191、LVGL 接收 190 帧，
主动跳过和待显示覆盖均为 0，AAC 丢弃为 0；不能据短测试判定长期音频稳定。
直播画面内容随时间变化，这些计数用于定位各阶段差值，不构成严格的版本帧率对照。
相同 480p 素材的两轮 80 帧纯解码为 5470/5290 ms，哈希均为 `a5eefb09`，
与优化前一致。纯解码速度不能作为完整播放器帧率。
`desktop cpu-status` 可核对播放时 `ui_mask=1 workers=1`，结束后
`ui_mask=3 workers=0`。主机只负责导入离线素材，播放没有电脑实时处理。

融合运动补偿滤波和平均的实验实现保留为诊断选项，默认 `BILI_P4_MC_DEFAULT=0`，
即关闭。模式 1/3 在同一固件中的六次配对测试虽然与原解码像素一致，
平均纯解码时间却从模式 0 的 6065 ms 增至 6120/6195 ms，因此不采用。
实验函数仍占内部代码空间；本版属于带诊断功能的优化固件。
完整记录位于本地 `output/media-v3-decode-affinity-scoped/RESULTS.txt`。

随后接入板上 PPA：通过同步 `/dev/ppa0` ioctl 做 UYVY→RGB565 和支持的缩放，
DMA 完成中断唤醒工作线程，带 250 ms 超时复位和软件回退。解码输出先打包为 UYVY；
不精确匹配硬件 1/16 步长的适屏比例在打包阶段映射，保持原来的显示窗口大小。
像素缓冲按 128 字节对齐，传输前后维护缓存。PPA 的插值与旧软件最近邻缩放可能不同。
本地 H.264 和直播适屏显示默认启用；直播原尺寸模式保留原来的软件路径。

同一固件上对相同 848×480 + AAC 文件按“软件/PPA/PPA/软件”交替测试：
前 60 样本的平均渲染耗时从 1795 ms 降到 1370 ms，约减少 23.7%；
解码计时从 5355 ms 略增至 5510 ms，读取/解码/渲染/等待合计从 7265 ms
降至 6900 ms，约减少 5.0%。两种模式前 60 样本平均都提交 31.5 帧，
因此没有证明 480p 显示帧率提高，尚未达到稳定 10 fps。
640×360 两次完整 8 秒短片都提交全部 80 帧，正常结束；计数仍不等于 LCD 刷新。

`desktop ppa-test` 检查灰阶和彩色条纹、缩放、填充行跨度和缓冲边界；
`desktop ppa-mode 0` / `desktop ppa-mode 1` 可做同固件对照。
本版驱动只适用于已验证的 P4 v3.x flat 配置，独占 DMA2D；其他硬件 JPEG/PPA
用户接入前须统一资源管理，不能各自重置 DMA2D。当前 JPEG 播放仍用原软件解码器。
完整记录位于本地 `output/media-v3-ppa-irq/RESULTS.txt`。

同日进一步进行三路真实直播验收：B站房间 6 的原生 854×480 连续运行约 3 分钟，
PPA 开/关/开三个检查段的渲染提交帧率约为 3.47/3.22/2.49 fps；
内容随时间变化，不能据此认定 PPA 带来了因果意义上的帧率提升。
累计丢弃 1008 个 AAC 包，后段仍有新增，音频稳定性未通过。
虎牙 660000、网易 CC 163163 各检查约一分钟，均为 800×450，
检查段分别约 3.95/2.96 次渲染提交每秒；AAC 分别累计丢弃 288/144 包。
虎牙丢包集中在启动期，CC 的检查段仍新增 48 包。
三路均能正常停止并恢复桌面双核调度，没有 PPA 超时或回退；停止后内部堆空闲
均为 61816 字节，用户堆约 27.39 MB。没有证明稳定 480p 10 fps 直播显示。
原始日志、命令时间线和汇总位于本地 `output/live-test-20261013/`。

调试固件提供 `desktop test-disk`，通过用户堆建立 2 MiB 临时 `/dev/ram9`；
重复创建会拒绝。只有确认它由该命令新建、未挂载时，才可将这个 RAM 设备
格式化为 FAT 并挂载至空闲的 `/sdcard`。不要格式化真实 SD 卡。
`desktop receive /sdcard/<name>.mp4 <bytes>` 可前台导入 Base64 测试文件，
上限 512 KiB，拒绝覆盖已有文件并返回长度及 CRC32；主机核对后才开始播放。
接收器每 48 个 Base64 字符确认一次，主机等待 ACK 后续传，避免串口接收丢字节。
PSRAM 文件在复位或断电后消失，测试设备占用的缓冲同样在复位后回收。

## 安装和构建

需要准备好的新版 v3 NuttX/Apps、GCC 14.2 ILP32F 工具链和已匹配的 TLS/ESP-DL 静态库。
本仓库是 overlay；本次复用本机已准备的 `/tmp/v3-desktop-espdl-20260915`，不宣称全新机器
可直接构建。`tools/build_bilibili_v3.py` 将其复制到独立构建树，应用当前 overlay、
清理旧系统对象并重新编译，复用库的哈希写入 BUILD-METADATA.json。

```sh
python3 tools/build_bilibili_v3.py \
  --baseline /tmp/v3-desktop-espdl-20260915 \
  --workspace /home/streetartist/p4-bilibili-v3-current \
  --toolchain /home/streetartist/.espressif/tools/riscv32-esp-elf/esp-14.2.0_20251107/bin \
  --archive /path/to/openh264-2.6.0.tar.gz \
  --output out/bilibili/v3 --jobs 4
```

OpenH264 tar SHA256 为 `558544ad358283a7ab2930d69a9ceddf913f4a51ee9bf1bfb9e377322af81a69`。
安装器不下载另一份 TLS。系统 `/data` 位于 `0xc00000`，模型区从 `0x800000` 开始，
固件从 `0x2000` 写入并检查不得覆盖模型区；不要擦除或格式化现有数据。

## 实板诊断

NSH 使用新版既有的 UI 请求队列，由桌面线程操作 LVGL：

```text
desktop ui bilibili
desktop ui bilibili-play:12005649
desktop ui huya-play:660000
desktop ui cc-play:163163
desktop ui current
desktop ui bilibili-stop
free
```

`desktop ui bilibili-stop` 返回桌面并释放会话。也可用触摸“停止”留在当前页。
实际验证范围见 [VALIDATION.md](VALIDATION.md) 和 [MULTI_PLATFORM.md](MULTI_PLATFORM.md)。

直播修复：排队丢帧不再作废正在完成的画面；不因墙钟落后而拒绝所有关键帧。
音频队列溢出只丢弃旧压缩包，保留 AAC 状态和 PCM 设备；网络读取采用 16 KiB 有界缓存，避免 FLV/HTTP 小头部反复跨 C6 传输。
