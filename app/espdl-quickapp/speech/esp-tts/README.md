# 乐鑫中文 ESP-TTS 与 boll 连续对话

当前可复现入口见 [完整流程](WORKFLOW.md)：依赖准备、离线回归、完整固件、SD 音色部署、
实板播报与失败回滚。2026-10-19 起，启用语音的完整构建默认使用 ESP-TTS 和经过 SHA-256
校验的 SD 官方音色，以保留现有数据分区；下文 2026-10-17 记录对应历史 flash 音色镜像。

使用官方 ESP-SR v2.4.6，提交 `cfdbb52172d4f1b3e5f7469d6c3c6e5dd0738143` 的
ESP32-P4 静态库和 `esp_tts_voice_data_xiaoxin_small.dat`。这是音节拼接式中文
合成，语音数据采用官方格式，不是自行训练的神经 INT8 模型。

`tools/build_speech_runtime.py --esp-tts-prepared <artifact>` 校验每个原始库、头文件、
语音数据的 SHA-256 后构建，并用 `GLASS_ESP_TTS` 将日常中文播报切换到乐鑫。
原始文件和许可保留在 artifact 中；构建记录保存原始来源、适配后库哈希、源码
哈希和 `tts_backend=esp-tts`。独立运行时构建未提供该选项时仍使用原后端；完整固件构建的
当前默认行为见上面的完整流程。

```sh
python3 tools/prepare_esp_tts.py --output /path/to/esp-tts-prepared
python3 tools/build_speech_runtime.py --apps /path/to/apps \
  --vendor /path/to/speech-vendor --output /path/to/esp-tts-build \
  --toolchain /path/to/gcc14/bin --esp-tts-prepared /path/to/esp-tts-prepared
```

完整固件构建器 `tools/build_bilibili_v3.py` 也接受 `--esp-tts-prepared`，
与原来的 `--speech-runtime` 一起使用；配置、分区与其他依赖沿用该构建器原参数。
链接时须包含构建结果 `compile.json` 列出的 `esp_tts_libraries`。

## 日常语音与连续对话

`glass_speech_say` 使用 `glass_esp_synthesize` 产生 16 kHz PCM，先在堆上缓存
当前短句，再以每块 576 帧连续送入现有播放器。官方合成调用的分块不均匀，
缓存用于避免播放期间等待解析或解码；代价是开口前增加整句合成耗时。缓存按需
增长，上限为 180 秒单声道 PCM（5.76 MB），播放完成或失败即释放。
每次调用独占可写模板、官方句柄和解析状态，完成、
出错或取消均释放资源，再由语音线程发布空闲。当前完整构建从 SD 加载并缓存经过校验
的官方音色，历史镜像将音色嵌入固件；日常乐鑫播报不依赖 Sano 模型。当前响度处理、
音量设置与缓存策略详见 [完整流程](WORKFLOW.md)。唤醒模型与联网语音识别的原有配置
要求保持不变。

App 内全局唤醒默认开启，大球页没有单独的唤醒开关。说“你好 openvela”或点球开始后，现有状态机依次完成联网识别、共享 AI 对话、分句播报、音频
清理、600 ms 等待和重新聆听。未听到内容会继续听，网络或鉴权故障会停止并
提示；点球打断回答后继续听，“结束对话”口令或按钮只结束当前会话，恢复全局唤醒。由唤醒启动的会话没有听到内容时也回到全局待机。退出页面
会停止本页面拥有的麦克风和播报，全局唤醒继续工作。当前是半双工：播报期间不开麦克风。大球页的唤醒直接使用页面内的大球，不显示小球浮层；其他页面才显示左下角小球与气泡，仅在连续空闲 6 秒后收起；语音输入、识别、AI／工具执行、设备核对或播报期间保持显示，完成后重新计时。浮层与大球共用 app 球体素材、正视和表情；浮层录音中切入大球页时隐藏浮层，将原录音交给大球继续，不重开麦克风。

```text
desktop ui voice
desktop ui voice-tap
desktop ui voice-status
desktop ui voice-end
```

状态诊断分别报告球的阶段、ASR、播报和 AI 状态，播报后端应为 `esp-tts`。

AI 结果在小球浮层和大球页使用同一套结果卡片，显示处理中、设备状态、执行已确认、结果待确认或任务未完成。执行确认取自原生工具返回的 `verified` 回执，不从 AI 回复中的“成功”字样推断；旧记录没有确认字段时也不补作成功确认。

已移除按用户语句关键词推断设备意图并替换回复的逻辑。设备卡片和确认状态只读取真实工具回执；普通 AI 回复保留原文并按顺序播报。必要参数不明确时由助手询问，不在本地猜测或改写指令。

小球的语音指令提交后跟踪本次对话编号，接收结果卡片并自动播报。设备结果逐张播报名称、状态和百分比；未确认的控制明确读作“结果还没有确认”。普通回答分段播报 AI 回复，重复刷新不会重播或重发工具命令。播报失败保留卡片；音频持续占用时最多等待 10 秒，之后提示结果已保留。处理和播报期间不自动收起，全部结束后连续空闲 6 秒才退下。进入大球页仍不弹小球，当前结果由大球页展示。

联网时录音使用每块 960 字节的立体声 PCM，保持 16kHz／16bit 采样和单声道下混；缩小应用缓冲与 I2S 内部 DMA 复制块，减少小型内部堆的压力，不改变语速或音量。ESP-TTS 播放参数不变。
官方库的逐字 INFO 日志只在这份 TTS 库中重定向并抑制，保留 WARN/ERROR，
不修改系统全局日志设置。

日常语速使用官方 `esp_tts_stream_play` 参数，范围为 0（最慢）至 5（最快）。
针对用户反馈的字间分离，默认由 2 调到 3，并提供串口对照入口：

```text
desktop speech speed
desktop speech speed 2
desktop speech speed 3
desktop speech speed 4
```

设置只影响随后开始合成的短句，同一句取开始时的固定档位；不改变 16 kHz
播放采样率，不保存到设备配置，重启恢复默认 3。导出诊断同样在开始时读取
当前档位，并在日志中记录；旧的 2 档 PCM 摘要仅适用于 2 档。该调节不改变
官方拼接法的音源和上下文韵律能力，
不能仅凭速度增加断言字间衔接问题已经解决。

播放日志同时报告 `prebuffer frames/render_ms` 与
`playback frames/expected_ms/elapsed_ms`。预期时长按有效样本数除以采样率计算，
实际耗时覆盖打开播放器至 drain 完成；软件计时不能替代扬声器录音的连续性检查。
`tools/test_speech_buffer.py` 提取生产缓冲函数，用 ASan/UBSan 验证完整合成后才
开始播放、样本顺序、分块上限、取消、内存分配失败与长度边界。

## 测试入口

```text
desktop speech esp-tts
desktop speech esp-tts-play
desktop speech esp-tts-export
desktop speech stop
```

前两条命令经持久 UI 任务启动语音线程，依次合成三条固定句子，第二条还在 P4
上播放。PCM 为 16 kHz、单声道、16 bit。合成结束后，以有偏移的短十六进制行
导出原始 PCM；主机检查完整长度、连续偏移及 SHA-256，保存为 WAV。导出节流
和播放等待不计入 `compute_us`，计时仅涵盖解析和官方流式合成调用。当前系统
单调时钟分辨率约 10 ms，不能把小于一个 tick 的测量值解释为零开销。

测试句包含“如果明天阳光很好，我们就去公园散步”和新的“河边散步”语境。
固定句命令仍是独立诊断；日常播报通过上面的 `glass_speech_say` 入口验证。

`esp-tts-export` 不播放、不逐行输出 PCM，而是将三个固定句的原始波形写入
`/sdcard/speech/test/esp-tts-s<speed>-c<case>.pcm`。先写临时文件，完整关闭后
重命名，失败时删除临时文件并报错。电脑通过已有配对文件接口下载，必须核对
样本数与设备端 SHA-256，再封装为 16 kHz、单声道、16-bit WAV；不重采样或归一化。

## 存储适配

此固件的早期静态 RAM 有严格边界，官方模板的 `.data.template_sylls` 指针表
占 6,856 字节。构建只将该表的存储节改为只读；语音线程在调用官方接口前复制
为独立的可写指针表，结束时释放。官方库的指令及合成算法保持原样。
`esp_tts_voice_set_free` 只释放实例本身，指针副本由适配器负责释放。

## P4 播放适配

当前板级 `esp_i2s.c` 的缓存行对齐分支会把一段缓存行尾部保存在只有四字节的
`tx.carry.value` 中。ESP-TTS 输出不规则短块时，该路径会越界，随后出现异常
巨大的 DMA 长度和 `I2S transfer failed: -27`。增加 DMA 描述符不能解决越界。

`glass_music_pcm` 现在跨写调用累积 576 帧，提交的双槽 PCM 长度始终为
64 字节的整数倍，绕过该驱动路径。`drain` 提交最后不足一块的数据，只在最后
补齐最多 15 帧静音（16 kHz 时小于 1 ms）；有效播放计数不包括补零。取消时
丢弃尚未提交的尾段，继续沿用 STOP 后释放缓冲的流程。这是应用播放适配，
该对齐适配位于应用层；codec 错误上报修复另述。直接调用 I2S 的其他路径不在
对齐适配覆盖范围内。

后续语速对照中实际捕获到 `Failed to allocate the DMA internal buffer [4608 bytes]`
与 `I2S transfer failed: -12`，失败块被 codec 清成 `nbytes=0`，但 DEQUEUE 的错误
状态没有送到应用。播放器因此曾把未发送块计为成功，出现 2,931 ms 音频仅耗
2,170 ms 的异常。四个 APB 的块长由 1,152 减为 576 帧，使队列及 DMA 副本的
音频数据占用减半，保留 64 字节对齐。codec 在返回失败缓冲前显式上报
`AUDIO_CALLBACK_IOERR`，应用收到该消息报 `-EIO` 并停止播放。正常输出缓冲
也会被 audio upper half 清零，因此不能用 DEQUEUE 后的 `nbytes` 判断成功。
主机回归包含错误消息不计入播放，以及两种 callback ABI 下错误先于 DEQUEUE
上报、引用释放与临界区配对的检查（`tools/test_es8311_return.py`）。

最新部署记录见
[verification.json](../../evidence/2026-10-17-esp-tts-playback/verification.json)。
镜像 `5905f6b0b96676860527c1725001acb5c0e14fdb72bbdb246271344d617108fc`
已保留在实板，3 档聆听已恢复。2 / 3 / 4 / 3 档连续测试的预期与实际播放耗时

串口 PCM 行每次携带 32 字节数据，摘要单独输出，降低长记录丢失的风险。
当前 USB 控制台仍偶发漏字符；不能把一次导出完成当作传输校验成功。主机必须
同时检查偏移、样本总数和设备 SHA-256。不同轮次的数据只有在设备报告相同
样本数和完整摘要时才能补齐，最终完整 PCM 仍必须匹配摘要。无法补齐并验证的
录音不能用于试听或比较音质。

主机回归可在安装 GCC 的 Linux/WSL 中运行：

```sh

```

90 组分块组合的样本顺序、双槽值、缓存行对齐、尾部静音、缓冲边界和回收计数，
并启用 AddressSanitizer / UndefinedBehaviorSanitizer。它不替代实板驱动验证。
