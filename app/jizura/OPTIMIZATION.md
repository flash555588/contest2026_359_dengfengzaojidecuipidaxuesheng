# JIZURA 无损优化原型

日期：2026-10-18。基于锁定的 0.10.1，在独立构建目录应用补丁，原版 `upstream/` 不变。目标是减少 P4 移植时的字形处理与缓存压力，保留全部 860 个效果注册项及 27 套风格；当前结果来自主机和浏览器，还不是固件实板验收。

本文记录第一轮结果；当前默认构建包含 [第二轮热点优化](OPTIMIZATION-STAGE2.md) 和 [第三轮排版／画布优化](OPTIMIZATION-STAGE3.md)，同时重建固定的第一、第二轮引擎供对照使用。

## 已实现

- **扫描标记替代洪泛栈。** 不再复制全图 Alpha，也不再建立与像素数相同的 32 位 DFS 栈。并查集保存临时连通关系，最终按首个前景像素顺序编号，保持原版碎片顺序。标签默认 16 位，超过 65,535 个临时分量时提升为 32 位。
- **三行快照替代整图膨胀副本。** 保留两次同时膨胀、左／右／上／下优先级以及原版散点合并与平局处理。阈值、字形分辨率和几何数据不变。
- **无损 A8／RLE 字形存储。** 缓存单通道 Alpha；有收益时使用 16 位游程长度＋8 位 Alpha 编码。白色精灵按需重建，染色仍使用原版 Canvas `source-in`，保持 Alpha 和颜色舍入。
- **4 MiB 精灵图像 LRU。** 白色与染色 Canvas 共用字节预算；淘汰图像时保留字形碎片身份和分解结果，避免改变碎裂动画用到的随机编号。超过预算的单张图像临时使用，不作为常驻缓存。
- **解释器热点优化。** 相同标签不重复调用并查集合并；按行计算包围盒，减少取模、除法和高频函数调用。

没有通过关闭色差、转场、模糊或碎片来换取结果。原字体栅格化、效果代码和参数保留。缓存限制仅针对保留的精灵图像，不是整个应用的 4 MiB 内存上限；字形几何与压缩遮罩仍受原版 1800 条目策略管理。

## 验证与测量

`tests/glyph-kernel.cjs` 从锁定源码直接提取原算法作为 oracle，265 组样本比较完整标签、包围盒、面积和散点映射；包含空图、边界、对角连通、随机 Alpha 和 66,049 个分量的 32 位提升用例。全部一致。

浏览器页面使用两个独立引擎上下文，相同字体、歌词、随机种子和时刻。覆盖 54 个真实字体／字符／分辨率组合，比较碎片几何、编号、碎裂多边形、白色及染色像素；在 32 KiB 精灵缓存下强制淘汰后再比较。随后覆盖 860 个注册项、27 套风格、透明／前后景／键色／统一模式、非顺序定位和 1024×576 样本。

最终版本 **4,369 帧、0 差异通道、0 警告／异常**。完整结果保存到工作区 `output/jizura-optimization-evidence/browser-results.json`，摘要见 [OPTIMIZATION-RESULTS.json](OPTIMIZATION-RESULTS.json)。这些是有限参数样本的等价性证据，不声称穷尽全部效果组合或全部字体。

回归中曾出现后续镜头差异；仅加载三个基础字体角色不足以固定所有样本。测试页补齐全部字体角色、ASCII 与原版字符池的预载后，最终回归差异归零。字体加载状态纳入记录，避免将异步加载或回退字体变化当成算法差异；此前的失败记录保留在本地 `browser-review.json`。

| 测量 | 原版 | 优化后 | 范围 |
| --- | ---: | ---: | --- |
| 512 桶字形分解数组（743×743） | 7,176,637 B | 约 1,109,600 B | **减少约 84.5%**；不含共享 RGBA、原生画布、输出遮罩和 VM 对象 |
| 54 个字形样本的常驻遮罩／精灵存储记账 | 约 37.4 MiB | 约 4.1 MiB | **减少约 89%**；不是浏览器进程 RSS 或整机堆峰值 |
| 同版本 QuickJS 合成字形内核，16 MiB 限额，3 次中位数 | 941 ms | 683 ms | **耗时减少约 27.4%**；64 位 Linux 主机、ASan／UBSan，非 P4 时间 |
| 同一独立内核的最低已通过测试限额 | 12 MiB | 6 MiB | 测试点为 4／6／8／12／16 MiB；包含合成 RGBA，不含完整引擎和原生画布 |

QuickJS 原版内核在 8 MiB 限额下报 OOM，优化内核在 6 MiB 下通过。两者使用同一份 QuickJS 2024-02-14 源码，关闭 BIGNUM；通过样本的分量数均为 3。计时不包含完整 Canvas 绘制。

优化后的完整引擎字节码为 2,035,470 B，在 8 MiB JS 限额、64 KiB 主机栈保护下通过全部注册表检查及 12 镜头默认规划。检查后 JS `malloc_size` 为 4,743,672 B，比原版探针多 10,263 B。该主机字节码尚未作为 P4 可部署文件验证。

**整帧速度尚无一致提升。** 对比页另外测量三套风格各 144 个稳态样本，结果包含不同程度的提升或回退；受字形图像缓存淘汰及 Canvas 调度影响。页面报告的是 JS／Canvas 命令提交耗时，没有测量 GPU 呈现完成，也不能据此声称 P4 达到多少 FPS。此轮最明确的收益是工作数组、缓存占用和 QuickJS 字形内核耗时。

## 查看效果

从本仓库根目录运行：

```powershell
python tools/jizura_optimized.py build
python tools/jizura_optimized.py serve
```

打开 <http://127.0.0.1:8768/optimization.html>。左右同步播放原版与优化版本；可切换风格、拖动位置、运行逐帧检查和导出 8 秒 MP4。页面中「打开优化编辑器」进入完整中文编辑器，全部原版编辑与导出入口保留在独立构建的 `optimized/zh-hans/`。

本轮实际导出的演示位于工作区 `output/jizura-optimization-evidence/optimized-demo.mp4`，另有便于查看的 GIF 和对比页截图。视频已用 ffprobe 核对为 H.264、640×360、24 FPS、8 秒，未添加音轨；这是优化后原引擎的浏览器导出，不是 P4 屏幕录像。完整中文编辑器入口也已实际打开，确认歌词、时间轴、方案与各类导出入口正常显示。

构建工具先核对 165 个原版文件，并验证七种原版语言输出仍逐字节一致，再应用有唯一锚点检查的字体补丁。`optimization-build.json` 记录两套引擎 SHA-256。

独立内核对照测试：

```powershell
node app/jizura/tests/glyph-kernel.cjs
```

Linux／WSL 中复测 QuickJS 内核（先运行可行性文档中的原版 QuickJS 探针，生成 BIGNUM 关闭的编译对象）：

  --apps /home/flash/vela-p4/v3-media-current/apps \

## 对 P4 的意义与剩余工作

`port/glyph-kernel.js` 不依赖 DOM，已在板端同版本 QuickJS 主机环境运行；A8／RLE 遮罩也适合后续原生 Surface 后端。下一步应把这些结构接入 P4 的实际字形栅格与画布绑定，测量音频和显示并行时的峰值内存及耗时。

此轮尚未实现完整 Canvas2D 的 P4 后端，也没有改变固件或烧录。不能把本轮浏览器等价和 QuickJS 主机收益算作板端全效果实时运行。原生路径、混合／滤镜、字体度量、离屏层预算及长曲缓存仍是下一阶段的验收项。
