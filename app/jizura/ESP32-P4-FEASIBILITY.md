# JIZURA 在 ESP32-P4 上的移植可行性

评估日期：2026-10-18。对象是本目录锁定的 JIZURA **0.10.1 / fc16bfe43ea4a6c25a21f1caf04d17326de14f00**，以及现有 openvela/NuttX 图形终端；不是另起 ESP-IDF 工程。此轮只增加分析工具、主机探针和报告，实板仅执行只读查询，没有烧录或变更播放器状态。

## 结论与范围

**完整文字 PV 播放引擎有继续移植的依据，但尚未证明所有效果能在 P4 上实时运行。原版网页不能直接作为当前快应用启动。** 已验证原版注册表、歌词解析和默认镜头规划能在与板端同版本的 QuickJS 主机环境运行；主要缺口是 Canvas2D、字体与图像处理后端，以及原版的峰值内存分配方式。

保持 860 个效果注册项、27 套风格和原版项目语义作为目标；早期八种 C/LVGL 布局不代表完整移植。播放引擎、完整编辑器、音频分析与导出均属于原版功能范围，以下逐项标明依赖，不把未迁移项默认为完成。

后续已实现扫描字形分解、无损 Alpha／RLE 和按字节管理的精灵缓存；主机／浏览器对照与实测见 [优化记录](OPTIMIZATION.md)。下文内存算术保留原版基准，优化结果不等于已完成板端绘图后端。

| 功能 | 现有依据 | P4 判断 |
| --- | --- | --- |
| 原版表达包、歌词解析、项目／镜头规划 | 同源 QuickJS 主机探针通过 | 可复用原 JS，需补目标板验证 |
| 原版全部效果的逐帧绘制 | 桌面浏览器基线累计渲染 4162 帧；没有 P4 绘图结果 | 有条件可做，Canvas2D／字体后端是首要门槛 |
| 音乐播放、暂停、定位同步 | 当前系统已有原生音乐服务 | 需用真实音频播放时钟驱动画面，验证暂停、拖动和缓冲恢复 |
| 完整简易／详细编辑器、撤销、时间轴、文件与字体管理 | 原版依赖 DOM、事件、浏览器存储及文件接口 | 无法直接运行；需 UI 和平台接口适配，工作量显著大于播放器 |
| 音频解码、节拍与能量分析 | 浏览器依赖 Web Audio | 需原生解码、FFT／分析接口及流式内存方案 |
| 项目 JSON、LRC、AE 数据 | 原版浏览器基线实际生成 | 序列化逻辑可复用，下载接口替换为文件服务；AE 本体仍在电脑端 |
| 普通／透明／分层 PNG 序列 | 原版浏览器基线实际生成 | 需原生 PNG、ZIP 和 SD 流式写出；速度待测 |
| H.264＋AAC MP4 | 浏览器样本已导出，不是板端结果 | 需视频编码、音频编码及封装链路，当前 openvela 未具备该完整路径 |

将电脑原版编辑器作为创作入口、P4 读取项目播放，是可先验证的部署方式；它不能被称为“P4 上完整编辑器复刻”。若要求全部编辑和导出都独立在 P4 完成，上表的每一行都需要单独验收。

## 实测与配置

### 实板资源快照

COM4 只读执行 `uname -a`、`free`、`mount`、`desktop ui music-status`：

| 项目 | 结果 |
| --- | --- |
| 运行环境 | NuttX / risc-v / esp32p4-function-ev-board，构建标识 `dd92bcf4-dirty` |
| 用户堆总量 | 33,554,432 B = 32 MiB |
| 当前用户堆空闲 | 27,011,648 B ≈ 25.76 MiB |
| 最大连续空闲块 | 25,387,192 B ≈ 24.21 MiB |
| 内核堆空闲 | 9,952 B ≈ 9.72 KiB |
| 文件系统 | `/data` smartfs、`/sdcard` vfat 均已挂载 |

这是查询当时的状态，不是 JIZURA 可独占的预算。音频、网络、桌面和其他服务还会申请内存；PSRAM 空闲不能代替内核堆、DMA 对齐和内部 RAM 预算。

固件分析使用独立快照 `output/jizura-p4-feasibility/firmware-snapshot/`（来源为 `output/jizura-pv-variety-review/firmware/`），复制前后核对三份文件的 SHA-256 一致。其 `nuttx.bin` 为 **8,875,412 B**，SHA-256 `238b815d0dd83fab76626d68f40b526b049d016e8394cbad560dd0be11eb0ed2`。按该镜像的应用区 `0x2000..0xc00000` 计算，距数据分区约剩 **3,699,308 B / 3.53 MiB**。这是快照产物的空间分析，不断言它就是此刻板内固件。

该 ELF 的 `.iram0.text` 68,258 B、`.dram0.data` 93,332 B、`.dram0.bss` 292,540 B；`_ebss` 到链接安全边界仅有 324 B，属于该布局的静态链接余量，**不是剩余堆**。新增大型静态数组不能直接放入内部 BSS。归档 `.a` 的合计包含未链接对象，ELF 的 dummy／debug 段也不能重复计入实际运行占用。

冻结配置启用双核、400 MHz CPU、200 MHz PSRAM、LVGL 软件绘制和 Canvas；未启用 LVGL Vector Graphic、ThorVG、FreeType。QuickJS 为 **2024-02-14，BIGNUM 关闭**。当前快应用内存上限取启动时空闲用户堆的一半，JS 栈保护值仅 **16 KiB**，不宜直接承载本引擎。

### QuickJS 同源主机探针

探针编译板端使用的 QuickJS 源码，关闭 BIGNUM，开启 ASan／UBSan。拼接原版 40 个 JS 文件，共 **2,268,835 B**。最小环境跳过 DOM 编辑器初始化，Canvas 字体度量接口故意报缺失，不伪造绘图成功。

| 检查 | 结果 |
| --- | --- |
| 效果注册项 | layout 184、enter 125、hold 52、exit 109、decor 130、treat 62、bg 66、cam 36、fx 69、trans 27，共 **860** |
| 风格／解析／规划 | **27** 套风格，测试歌词 2 行，默认项目 **12** 个镜头 |
| 源码加载 | 8／12 MiB JS 分配限额失败；16 MiB 及以上通过 |
| 预编译字节码 | 2,031,484 B；最低测试限额 **8 MiB** 通过 |
| 字节码模式完成检查后的 JS 分配统计 | `malloc_size` 4,733,409 B，约 **4.51 MiB** |
| 字节码模式栈保护检查 | 16／32 KiB 在检查／规划阶段溢出；64／128 KiB 通过 |

这些是 **64 位 Linux 主机**数据，不能作为 32 位 P4 的精确内存、速度或栈需求。JS 分配统计不包含全部进程开销或未来原生画布。64 KiB 是主机测试通过点，不是已确定的板端配置。字节码必须与目标 QuickJS 版本、选项及字节序验证匹配，当前主机生成文件不直接作为目标发行包。

注册项存在和默认规划成功不等于 860 个效果在 QuickJS 中已经绘制。之前的 4162 帧来自真实浏览器，仍不代表所有参数组合或板端兼容性。

## 主要障碍

### Canvas2D 比 JS 解释器更关键

静态扫描命中 **35 类方法名、16 类合成／混合模式字面量**，包括路径、裁剪、任意仿射变换、渐变、文字度量、图像采样及读写；还出现 blur、contrast、grayscale、hue-rotate、invert、saturate 等滤镜字面量。扫描按文本匹配，可能包含同名非 Canvas 调用，不能替代完整 API 兼容测试。

现有板级 `P4_PPA_SRM` 只提供同步 UYVY → RGB565 缩放转换，128 B 对齐，驱动旋转固定为 0；它尚不提供原版需要的 RGB／ARGB／A8 合成、任意旋转、复杂混合、滤镜、路径及字形碎片操作。

硬件 PPA 本身提供 SRM、普通 Alpha 混合与填充，可作为部分操作的加速后端；它不能自动实现完整 Canvas2D。缩放量化、双线性采样和 PSRAM 竞争也会影响字缘及吞吐，必须按操作测量。[Espressif PPA 文档](https://docs.espressif.com/projects/esp-idf/en/release-v5.5/esp32p4/api-reference/peripherals/ppa.html)

LVGL Canvas 也不是浏览器 Canvas2D 的直接替代。ThorVG 等矢量库可作为路径和变换实现的候选，但当前未启用，仍需验证文字、混合、滤镜、读回与采样语义，不能把“启用库”视为完成适配。

### 原版分配策略不能照搬

以下均是源码尺寸算术，不是已经测得的板端峰值：

| 16:9 渲染尺寸 | 单张 RGBA | 四张 RGBA | 六张 RGBA |
| --- | ---: | ---: | ---: |
| 512×288 | 0.56 MiB | 2.25 MiB | 3.38 MiB |
| 640×360 | 0.88 MiB | 3.52 MiB | 5.27 MiB |
| 800×450 | 1.37 MiB | 5.49 MiB | 8.24 MiB |
| 1024×576 | 2.25 MiB | 9.00 MiB | 13.50 MiB |
| 1920×1080 | 7.91 MiB | 31.64 MiB | 47.46 MiB |

四／六张是压力场景预算，不声称每一帧都同时分配这些全尺寸画布。原版按效果建立离屏层、模糊层和转场缓存，实际峰值必须逐场景记录。1024×600 屏显示原版 16:9 内容时，1024×576 可上下留边，避免拉伸文字。

`02_fonts.js` 的字形碎片分析使用 `S=ceil(res×1.45)`。RGBA 画布、RGBA 读回、Alpha、32 位标记、洪泛栈和一次标记拷贝合计约 `21×S²` 字节：

| 字形分辨率桶 | 上述缓冲合计 |
| --- | ---: |
| 128 | 0.69 MiB |
| 256 | 2.77 MiB |
| 512（默认上限） | **11.06 MiB** |
| 768（高分辨率导出路径可用） | **24.85 MiB** |

尚未包含碎片精灵、染色副本、字体、其他对象和 VM。原版噪声画布另外约 1 MiB；字形缓存按条目数淘汰，不能限制在固定字节预算内。仅 768 桶的上述缓冲加主机探针 JS 分配量就超过此次实板空闲；1024×576 六层场景加 512 桶缓冲、噪声和 JS 同样超过空闲。**直接照搬原版分配方式无法保证完整功能运行。**

即使单次全屏 RGBA 读／写，在 1024×576、30 FPS 下也有约 **135 MiB/s** 理论数据流量；多重采样、模糊、合成与显示 DMA 还会增加流量。这是最低数据量估算，不是实测带宽，也不能换算成板端 FPS。

### 字体与导出必须单独处理

原版按需使用浏览器字体加载及度量。当前 TinyTTF／LVGL 字体不能默认得到相同的字宽、基线、字重、描边和抗锯齿。完整迁移需管理对应字体及许可证，在 SD 上离线存放并按需读取；笔画分解使用同一字形栅格和阈值，与浏览器样本逐图比较。完整上游目录约 32.5 MB，不应直接嵌入只剩约 3.53 MiB 的应用区；运行所需引擎、字体和项目应拆分管理。

P4 有硬件 H.264 **编码**能力，不能据此推断有硬件 H.264 解码器或当前系统已有 MP4 导出。现有视频播放器使用的软件解码与原版 WebCodecs 编码是不同路径。板端导出还需 openvela 编码驱动／组件适配、AAC、MP4 封装和 SD 写入验证；4K／高帧率浏览器导出不能直接作为板端承诺。[Espressif 视频技术选型](https://docs.espressif.com/projects/esp-video-components/en/latest/esp32p4/Technology_Selection.html)

## 建议实现与验收顺序

1. **保持原版 JS 为语义基线。** 独立 QuickJS 工作线程承载规划及渲染调用，验证目标兼容字节码、明确堆／栈限额、取消及资源释放；不占用桌面 UI 线程进行整帧计算。
2. **先证明 Canvas2D 后端兼容。** 建立原生 Surface／Context 绑定，覆盖变换、路径、裁剪、渐变、文字、图像读写、合成与滤镜。先保证输出正确，再将合适操作交给 PPA；未支持操作显式报错，不能静默跳过效果。
3. **保持效果，改变内存管理。** 使用受预算控制的离屏池、明确所有权及复用；字形数据按字体／字重／字符／桶缓存，支持从 SD 读取预计算分解结果。原生分解或分块处理必须与原算法结果比对，Alpha 缓冲与按需染色需维持原版可见结果，不能靠减少效果宣称完整。
4. **接入音乐与完整交互。** 以音频实际位置驱动原版时间轴；LVGL 接收已完成帧并处理控制。随后适配编辑器、项目文件、字体选择、音频分析和导出，分别记录完成状态。
5. **再决定性能方案。** 先在目标分辨率上测量不同效果的耗时，再评估 1024×576、800×450、640×360 等渲染尺寸。分辨率、目标帧率或画质变更需单独标明，不能把降低参数的结果称为原参数达标。

进入“可交付”前至少需要这些实板证据：

- 与浏览器相同项目、随机种子、字体、时刻和参数，覆盖 860 个注册项及 27 套风格；保存参考图及差异，单独检查字形碎片、模糊、色差、多层转场和混合。
- 报告典型／压力场景的帧耗时分布、掉帧、用户／内核堆峰值、最大连续块和栈水位；音乐、触摸、Wi-Fi 同时运行，不能用空场景替代整机负载。
- 长曲播放、反复切歌、暂停／定位／恢复、进入／退出与内存回收；音画时钟误差随时间不持续积累。
- 编辑与各类导出分别验收；视频检查编码、音轨、时间戳和封装结果，PNG 检查透明度与分层。没有这些证据之前，不给出“全效果稳定 30 FPS”结论。

## 复现与证据

本仓库根目录运行：

```powershell
python tools/jizura_full.py verify
python tools/audit_jizura_port.py --output ../output/jizura-p4-feasibility
```

Linux／WSL，`--apps` 指向板端对应的完整 apps 源码树：

```bash
python3 tools/probe_jizura_quickjs.py \
  --apps /home/flash/vela-p4/v3-media-current/apps \
  --output ../output/jizura-p4-feasibility
```

需系统 C 编译器及 ASan／UBSan；默认从源码构建同版本 QuickJS，不复用 BIGNUM 不匹配的宿主缓存。8／12 MiB 源码限额及 16／32 KiB 栈测试预计失败，其余通过仅表示对应的解析／规划探针通过。

本次结果摘要见 [P4-PROBE-RESULTS.json](P4-PROBE-RESULTS.json)。完整本地输出位于工作区 `output/jizura-p4-feasibility/`：`quickjs-probe.json`、`static-audit.json`、`board-readonly.json`、`elf-sections.txt`、`elf-symbols.txt`、`codesize.json`。浏览器基线另见 `output/jizura-full-validation/`。这些本地输出不随 Git 克隆自动提供；可用上面命令重跑主机分析，板端资源则需在实际设备重新查询。
