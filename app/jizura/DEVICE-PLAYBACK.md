# ESP32-P4 的 SD 完整效果播放路径

本路径在电脑上用锁定的完整版 JIZURA 引擎渲染项目，再由 P4 从 SD 播放经过校验的 RGB565 帧。原版字体、文字碎片、纹理、装饰与转场烘焙进画面；P4 不加载整个字体包或浏览器画布。它与实时原生歌词共用音乐服务的实际 PCM 播放进度，关闭播放器不停止背景音乐。

这是 **SD 预渲染播放版**。不是 P4 的实时 Canvas2D 后端、完整编辑器或板端视频导出实现。27 套示例使用 16 种布局，并不表示所有 860 个注册项的全部参数组合都已在设备播放。更换歌词或构图需要重新在电脑渲染相应项目。

## 资源和恢复

- 输出为 640×360、12 fps。RGB565 量化对应设备显示格式；RLE16／LZ4 压缩均无损。另提供 JPEG 播放档，明确采用有损压缩，降低 SD 带宽需求。
- 两张帧缓冲固定 **921,600 B = 900 KiB**，流式读缓冲 32 KiB，索引窗口 768 B。JPEG 档另按需分配 128 KiB 输入与约 16 KiB 解码工作区。线程栈在 NuttX 配置为 8 KiB。以上不包含 LVGL、音频解码器、文件系统和系统字体缓存，整机占用以实板记录为准。
- SD 读取、解压与逐帧 Adler-32 校验在独立线程执行。UI 只切换已完成的后缓冲，并提前准备下一帧，按音频时钟显示。跳转直接读取目标帧的索引，落后的帧被跳过，不排队补播。
- 暂停后画面跟随 PCM 位置停止，不继续读盘。退出文字 PV 或关闭全屏页面会取消读取、等待工作线程结束、释放双缓冲并丢弃图像缓存。
- 文件缺失、身份不符、索引越界、截断、解压失败、校验错误或播放越过素材末尾时回退到原生歌词。一次失败不在每个 UI tick 重试；切换歌曲、风格或重新进入后可再读取。
- “减少动态效果”启用时使用原生静态歌词。音乐 MCP 的后台调用路径保持不打开音乐应用。

原生底栏收为 752×64 的单行浮动控制栏：播放按钮 48 px，前后曲与收藏触摸区 44 px；音量细线单独扩展触摸范围。时间、进度与音量不再分占两行。

## 文件格式

每个项目每套风格一个 `xxxxxxxx-NN.jpv`。前八位是歌曲名加 NUL、艺人名加 NUL 的 FNV-1a，`NN` 是 SD 风格表索引。文件头再次核对完整歌曲名和艺人名，避免仅依赖文件名散列匹配。

| 区域 | 内容 |
| --- | --- |
| 288 B 文件头 | `JZPV01`、版本、640×360、fps、帧数、时长、风格索引、128 B 歌曲名、96 B 艺人名 |
| 每帧 12 B 索引 | 文件偏移、低 30 位长度／高 2 位编码、Adler-32；编码 0–2 校验解码像素，编码 3 校验压缩数据 |
| 帧数据 | 编码 0 为 RLE16，1 为原始 LZ4 block，2 为原始 RGB565，3 为 baseline JPEG；每帧独立寻址 |

文件头偏移 260 的扩展标记为 `IDX2` 时，编码 1／2 改为 LZ4／raw 的固定 58,112 B 调色板帧：512 B RGB565 调色板和 320×180 的 8 位索引。仅允许这两种编码，校验的是完整调色板与索引；校验通过后在目标缓冲内逆序展开为 640×360。展开前先移走调色板前缀，避免覆盖首行尚未读取的索引。原有扩展标记为零的帧保持原语义；未知标记直接拒绝。

解码前校验文件类型、大小、尺寸、帧数、时间关系、字符串边界和每个索引。LZ4 的字面量、扩展长度、回溯距离和输出上限逐项检查。JPEG 输入上限 128 KiB，复用现有 TJpgDec 解码器。只保留 64 项索引窗口，不把整个索引表载入 RAM。

## 渲染与打包

从仓库根目录运行，准备好的字体和引擎目录见 [SD 素材说明](SD-ASSETS.md)：

```sh
python3 tools/render_jizura_banks.py --assets ../output/jizura-sd-20261018/sdcard/jizura --output ../output/jizura-device-20261018/banks-v2
```

打开命令输出的本机页面，点击“生成 SD 播放素材”。可用 `--project` 指定原版项目 JSON；项目 title 和 artist 必须与音乐服务中的歌曲身份一致。`--seconds`、`--fps`、`--styles` 指定导出范围。

调色板档先用 Pillow 生成固定索引帧，再用系统 liblz4 压缩；这两步可分别在 Windows 与 WSL 运行：

```sh
python3 tools/pack_jizura_indexed.py --source ../output/jizura-device-20261018/banks-v2 --output ../output/jizura-device-20261018/banks-indexed-raw
python3 tools/pack_jizura_banks.py --source ../output/jizura-device-20261018/banks-indexed-raw --output ../output/jizura-device-20261018/banks-indexed
python3 tools/test_music_pv_banks.py --banks ../output/jizura-device-20261018/banks-indexed --output ../output/jizura-device-20261018/codec-indexed
```

以下是完整分辨率的无损参考档；宿主工具不将动态库放入固件，该档的实板吞吐限制见下文：

```sh
python3 tools/pack_jizura_banks.py --source ../output/jizura-device-20261018/banks-v2 --output ../output/jizura-device-20261018/banks-lz4
python3 tools/test_music_pv_banks.py --banks ../output/jizura-device-20261018/banks-lz4 --output ../output/jizura-device-20261018/codec-lz4
```

本次 27 套、每套 96 帧，共 2592 帧：978,101,388 B → **544,267,769 B**，打包后全部解压内容一致。实际 SD 文件放在 `/sdcard/jizura/pv`；90.8 MB 的离线字体／引擎素材仍另存在 SD，设备播放帧库时不会整包读入内存。

实板无损档未达到播放要求：每帧平均读取和解码约 312 ms，其中 I/O 约 210 ms；2 MiB 顺序读耗时 1.74 s。该档不能据主机预览宣称流畅。JPEG 自适应档共 **141,166,797 B**，2592 帧主机解码通过；编码质量通常为 92，低于 30 dB 的 4:2:0 帧改用 4:4:4，最终最低 PSNR 为 30.078 dB。目录为 `/sdcard/jizura/pv-jpeg`，优先于无损档；实板帧率仍需独立验证。

`pack_jizura_jpeg.py --source .../banks-v2 --output .../banks-jpeg-adaptive --subsampling 2` 生成该档。`test_music_pv_banks.py` 同时输出 `decoded-adlers.json`；实板截图对照时通过 `test_jizura_device.py --decoded-reference` 使用同一解码器的 RGB565 结果，不能拿有损输出与原始无损像素直接比较。

完整分辨率 JPEG 实板平均仍约 200 ms，其中读盘约 55 ms，软件解码成为主要瓶颈，因此也未通过播放要求。新增 `--scale 2` 档：从完整引擎输出缩到 320×180 后编码，在同样的 640×360 显示区域内原地放大两倍，保留全部构图与样式，但细小纹理和文字会损失清晰度。27 套总计 **39,210,472 B**；该档的 PSNR 对照缩小后的源图，不能与完整分辨率档的 PSNR 直接比较。放大从缓冲尾部向前执行，无额外临时帧分配；主机逐像素检查放大结果与越界哨兵。预读使用目标帧的准确时间戳，播放中跳转先读取当前位置，不提前跨过下一帧边界。

实板还发现首帧等待期间重绘原生文字与重复设置整页配色会持续拖慢界面。现在等待 SD 时不绘制这套临时动画，配色仅在值改变时更新，解码线程显式使用低于桌面的优先级。上述修正后的半分辨率 JPEG 档已完成 27 套实板播放检查，观察换帧约 8.6–11 fps，仍未跑满素材的 12 fps。

全屏打开时，音乐页仍更新服务快照供收藏操作读取当前歌曲，但暂停被遮挡页面的控件与封面更新；退出全屏后的下一次刷新补齐页面，避免无关区域触发额外绘制。

进一步的 `pack_jizura_indexed.py` 档使用 320×180、每帧 256 色 RGB565 调色板，再由 `pack_jizura_banks.py` 无损压缩调色板和索引，共 **71,697,888 B**。调色板量化与缩放有损，最低 PSNR 31.224 dB 对照缩小后的源图。该档不申请 JPEG 输入与解码工作区，目标是减少解码 CPU 开销；是否更快必须以实板结果判定。42 组有效／损坏输入和全部 2592 帧已通过 ASan／UBSan，并用独立参考检查逆序展开后的全部像素。

## 部署和检查

`build_jizura_device.py` 限定更新音乐与相关 UI 文件，核对已验证构建配置、复用库哈希、内部 RAM 链接边界、应用分区末端和未链接语音实验符号，并保存回退镜像。`flash_jizura_device.py` 先核对设备身份及原镜像，只写 `0x2000` 的应用镜像，不写 `0xc00000` 起的数据分区。

`deploy_jizura_banks.py` 将已核对 SHA-256 的公开素材写入新暂存目录，核对逐文件大小后发布。`--resume-from` 复用已经完成的文件；中断文件保留。`--fast` 使用限定在私有局域网编号素材和 SD 暂存文件的新导入入口，缓冲 32 KiB、文件上限 32 MiB，`O_EXCL` 防止覆盖。该入口用于本次示例导入，无网络监听服务。

`test_jizura_device.py` 分阶段记录实板结果：`hashes` 逐文件 SHA-256，`smoke` 对照音频时钟、暂停与真实 framebuffer，`styles` 连续播放每套风格，`cycles` 反复开关和内存回收，`fallback` 检查缺失文件回退与恢复，`final` 留下暂停预览。原图与实板图的 640×360 区域应具有相同的 RGB565 校验值。

主机检查已包括 42 组有效／损坏输入、2592 个真实渲染帧、27 套原生播放预览、暂停不读盘、双向定位、缺失文件、减少动态效果及 60 次线程／缓冲创建销毁。实际部署与实板压力结果保存在工作区 `output/jizura-device-20261018/`；最终摘要在完成实板检查后更新。
