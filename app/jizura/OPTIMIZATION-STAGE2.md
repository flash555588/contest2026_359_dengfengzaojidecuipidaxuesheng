# 第二轮：精灵解码与帧内热点

基于第一轮无损优化继续减少 QuickJS 的逐像素与逐事件调用。原版 165 个文件不变；上一轮引擎由固定夹具重建，核对归一化 SHA-256 后参与对照。两轮结果分别记录，第一轮数据见 [OPTIMIZATION.md](OPTIMIZATION.md)。

## 实现

- **RLE 批量解码。** 使用同一 RGBA 缓冲的 `Uint32Array` 视图，按游程调用原生 `fill`，替代每个像素一次 JavaScript 闭包调用；不复制第二份 RGBA。按宿主字节序打包，透明像素继续为零。
- **按需染色。** 可直接从 Alpha 遮罩生成最终染色画布，减少为颜色副本额外生成白色画布的工作；仍使用原版 `source-in` 着色和 4 MiB 图像 LRU。
- **近期镜头事件二分查找。** 利用原规划器按时间排序的事件表，直接定位相机抖动／色差所需的近期区间。读取当前事件时间，不缓存过期的时间表；短表保留原遍历路径，年龄边界沿用原版的浮点运算。
- **活动事件循环。** 替代 `Array.filter` 的逐事件回调，帧间隔只计算一次；保留原事件顺序、长持续时间事件以及 NaN／无穷值的结果。长事件不能因为起点久远而被截掉。
- **复用固定渐变。** 每个绘图上下文保留背景与暗角两个槽位，尺寸、缩放、明暗或纹理强度改变时重建。没有增加整屏位图缓存。

修改位于 `port/sprites.js`、`port/frame-hot.js`，由构建脚本在独立输出目录应用。没有移除效果、降低渲染尺寸或改变动画参数。

## 对照方法

`tests/frame-hot.cjs` 对照第一轮实际解码代码和原版事件表达式，检查 1,099 个样本：全部 RGBA 字节、65,535 游程边界、随机 Alpha、上万事件、反向定位、长事件、特殊时长／FPS 和渐变失效条件。

浏览器渲染回归使用原版生成的同一份镜头计划，并为两套实现提供相同的数值字体度量快照；每套实现仍使用自己的本地度量函数、字形栅格和绘图代码。测试前重建独立引擎，避免预览历史影响碎片编号。性能组另外使用两个独立实例，完整预热测量时间范围，所有度量快照复制均在计时之外。

这种输入隔离是必要的：早期测试分别规划场景、或让计时实例继承不同的编号历史，曾产生输入不同的“渲染差异”。相关失败记录留在本地；最终数据只采用相同场景输入通过后的结果，不把这些失败当成优化通过。

验收包括原版全部 860 个注册项、27 套风格、54 个字形组合、透明与分层输出、1024×576 样本，以及改变画布尺寸／背景色／纹理强度后的画面。整帧性能组对照上一轮，覆盖黑白、纸张、红色三套风格与 20,001 条事件的合成压力场景，每组 96 个样本；计时包含完整 Canvas 像素读回，并逐样本比较画面。

## 结果边界

最终结果与构建哈希见 [OPTIMIZATION-STAGE2-RESULTS.json](OPTIMIZATION-STAGE2-RESULTS.json)。完整本地记录在工作区 `output/jizura-stage2-evidence/`。

最终验收：**4,384 帧原版对照、384 帧第一轮对照全部逐像素一致，0 警告／异常；1,099 个内核用例通过。**

| 主机 QuickJS 独立合成热路径 | 第一轮 | 第二轮 |
| --- | ---: | ---: |
| 743×743 RLE 遮罩展开为 RGBA | 154.58 ms | 1.33 ms |
| 20,001 条事件的相机／活动事件查询 | 14.33 ms | 7.42 ms |

每项为 3 组、每组 12 次的中位单次耗时；解码结果额外核对整个缓冲的哈希。遮罩展开不是第一轮报告中的连通分量分析，也不是整个字形生成流程。

| 浏览器完整帧＋读回中位数，640×360 | 第一轮 | 第二轮 |
| --- | ---: | ---: |
| 黑白 | 10.0 ms | 10.1 ms |
| 纸张 | 11.3 ms | 11.1 ms |
| 红色 | 10.2 ms | 10.7 ms |
| 长事件表合成场景 | 9.6 ms | 10.0 ms |

引擎字节码为 **2,036,893 B**，仍通过 8 MiB JS 限额下的注册表／默认规划探针；64 位主机检查后的 JS 分配快照为 **4,747,662 B**。这些值不包含原生画布、全部进程开销或整机堆峰值。

QuickJS 独立热路径测试使用板端同版本 **2024-02-14 / BIGNUM 关闭**的 Linux 主机构建，开启 ASan／UBSan。合成样本中 RLE 解码有显著收益，事件处理也减少了开销；这些数字不包含原生画布和 P4 硬件，不能换算成板端 FPS。

桌面 Canvas 的整帧中位数与 P95 仍有升降，尚无跨风格的一致提速。当前明确改善的是解释器热路径；混合、滤镜、字体栅格、图像上传与离屏绘制仍占据整帧成本。P4 的完整 Canvas2D 后端和实板帧率仍未验收，本轮没有烧录。

## 复现

从本仓库根目录运行：

```powershell
node app/jizura/tests/frame-hot.cjs
python tools/jizura_optimized.py build --output ../output/jizura-optimized-stage2
python tools/jizura_optimized.py serve --output ../output/jizura-optimized-stage2 --port 8769
```

打开 <http://127.0.0.1:8769/optimization.html>，运行「逐帧验证与测量」。`stage1-engine.js` 是上一轮基线，`optimized-engine.js` 是新版本；两者与原版的哈希写入 `optimization-build.json`。

Linux／WSL 中使用上一轮由同源 QuickJS 编译的 `quickjs-kernel` 探针运行：

```bash
python3 tools/test_jizura_frame_quickjs.py \
  --runner ../output/jizura-optimization-evidence/quickjs-kernel \
  --output ../output/jizura-stage2-evidence
```

原版源码、上一轮基线和本轮实现分别保留，后续修改可继续按相同数据和参数比对。
